# IAM Access Review

Read-only AWS IAM access review tool that checks identities against CIS-mapped rules.

## Why it matters

Most cloud breaches start with identity: a leaked access key nobody uses, a console user without MFA, or a user with full admin rights. A regular access review finds these before an attacker does. This tool automates the evidence-gathering part of that review and maps each finding to a control.

## What it checks

Benchmark: **CIS AWS Foundations Benchmark v3.0.0**. Framework: **NIST CSF 2.0**.

| Rule | Threshold | CIS v3.0.0 | NIST CSF 2.0 | Severity |
|---|---|---|---|---|
| Root has an active access key | any | 1.4 | PR.AA-03 | High |
| Root has no MFA | any | 1.5 | PR.AA-03 | High |
| Console user without MFA | any | 1.10 | PR.AA-03 | High |
| Password or access key unused | `--unused-days` (45) | 1.12 | PR.AA-05 | Medium |
| Access key older than threshold | `--rotation-days` (90) | 1.14 | PR.AA-01 | Medium |
| AdministratorAccess attached directly to a user | any | 1.16 | PR.AA-05 | High |
| Granted services unused (`--permissions`) | `--unused-days` (45) | none | PR.AA-05 | Medium |
| User exists but is missing from the credential report | any | none | none | Info |

**Unused credentials.** The tool ages a credential from its last-used date. If it was never used, it ages it from its creation date instead (for keys, the last-rotated date; for passwords, the last-changed date, then the user creation date). A key created today is not "unused for 45 days," so it is not flagged.

**Note on the unused-services check.** It is labeled `NIST PR.AA-05 (least-privilege check, no direct CIS test)`. CIS 1.16 covers policies granting full `*:*` admin rights, not unused services, so no CIS control is claimed. A never-used service is aged from the user creation date.

**Coverage gap check.** AWS reuses a credential report for up to 4 hours, so a user created after the report was generated is not in it. The tool compares the report with the live `ListUsers` API. Any missing user gets an Info finding ("not in credential report, re-run later") plus the live AdministratorAccess and unused-services checks. Its password, MFA, and key rules wait for the next report. Every Markdown report also prints when the credential report was generated and how old it was at run time.

**Note on CIS versions.** CIS v5.0.0 renumbers this section. For example, key rotation is 1.13 and full admin is 1.15 in v5.0.0. The numbers above are for v3.0.0, which matches AWS Security Hub's v3.0.0 mapping.

## Requirements

- Python 3.10 or newer
- boto3 (the only runtime dependency)
- An AWS CLI profile for a user with only the six read actions in [`auditor-policy.json`](auditor-policy.json):
  `GenerateCredentialReport`, `GetCredentialReport`, `ListUsers`, `ListAttachedUserPolicies`, `GenerateServiceLastAccessedDetails`, `GetServiceLastAccessedDetails`. `ListUsers` was added for the coverage gap check.

## Setup

```bash
git clone https://github.com/Hajis786/iam-access-review.git
cd iam-access-review
python3 -m venv .venv
source .venv/bin/activate          # Windows: .\.venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt
```

Create the auditor user with `auditor-policy.json` and store its key in a CLI profile with `aws configure --profile iam-audit`. Never put keys in code.

## Run it

```bash
python iam_review.py --profile iam-audit                         # default: 90 / 45 days
python iam_review.py --profile iam-audit --rotation-days 60 --unused-days 30
python iam_review.py --profile iam-audit --permissions           # adds unused-services check (slower)
python iam_review.py --profile iam-audit --unused-days -1        # demo only: flags every credential
python -m pytest -q                                              # unit tests, no AWS calls
python fixtures.py                                               # rebuild sample/ from fake data
```

Results go to `output/iam_review.csv` and `output/iam_review.md`. `output/` is git-ignored. The `-1` thresholds are a test setting to show the rules fire on brand-new users. They are not a real policy. With `--unused-days -1`, any active credential is flagged, even one used today (age 0 is greater than -1).

## How I verified it

I ran the tool against a dedicated AWS test account with dummy users, then compared every finding with the downloaded credential report.

1. **First run.** The tool flagged that the root user had no MFA. I turned MFA on.
2. **Stale report.** I created five test users, then ran it again, and it found none of them. AWS had reused a credential report from before the users existed. That's why I added the `ListUsers` coverage check. On the next run, all five users showed up as Info gaps, and the admin check still caught both users with AdministratorAccess.
3. **Lag on existing users.** I created a console password for `test-nomfa` 3 minutes after a new report. The tool did not flag it until the next report. A direct `GetLoginProfile` and `ListMFADevices` check confirmed the password existed with no MFA.
4. **Fresh report.** After the refresh, the tool's results matched the credential report:

| Run | Findings |
|---|---|
| Default | `admin-you`, `test-admin`: AdministratorAccess (High). `test-nomfa`: console user without MFA (High) |
| `--unused-days -1` | Default findings, plus `test-idle` key and `test-nomfa` password unused (Medium) |
| `--permissions` | Default findings. No unused services, because the users were under a day old |

Root came back clean once MFA was on. No real account data is stored in this repo.

## Limitations

- Credential report data can lag by up to 4 hours. Changes to existing users, such as a new password or MFA device, appear only after the next report. A live check would need direct API calls and more read permissions. The report header shows the data's age, and users missing from the report are flagged.
- The admin check only covers AdministratorAccess attached directly to users. It misses groups, roles, inline policies, and custom policies that grant `*:*`.
- The unused-services check uses service-level data, not action-level data.
- Root is checked only for root rules (CIS 1.4, 1.5).
- This is an automated control test, not a full audit. It does not judge business need.
